Comprendre le code du backend NestJS

Guide pédagogique basé sur le code présent dans Backend/typescript-starter/src et sur le PDF de consignes du projet.

Architecture GraphQL schema-first, logique métier, sauvegarde des mondes et progression temporelle.

1. Architecture générale

Le backend est une application NestJS. Le frontend envoie des requêtes GraphQL ; le resolver les reçoit et délègue les règles du jeu au service.

Frontend Angular | | requête GraphQL v schema.graphql = contrat de l'API | v resolver.ts = traduction des actions du joueur | v app.service.ts = règles du jeu et calculs | +--> origworld.ts monde initial +--> userworlds/{user}-world.json sauvegarde du joueur

Idée essentielle : schema.graphql décrit ce qui est possible, resolver.ts répond aux demandes, et app.service.ts décide réellement du résultat.

2. Démarrage et assemblage

main.ts

C'est le point d'entrée de l'application. NestFactory.create(AppModule) démarre NestJS avec le module principal.

  • useStaticAssets(.../public) rend les images de public accessibles par HTTP ;
  • enableCors() autorise le frontend à appeler le backend depuis un autre port ;
  • listen(... ?? 3000) démarre le serveur sur le port configuré ou sur 3000.

app.module.ts

Ce fichier assemble l'application avec le décorateur @Module.

GraphQLModule.forRoot({
  driver: ApolloDriver,
  typePaths: ['./**/*.graphql'],
  definitions: {
    path: join(process.cwd(), 'src/graphql.ts'),
    outputAs: 'class'
  }
})

Cette configuration active Apollo GraphQL, cherche le schéma dans les fichiers .graphql et génère les classes TypeScript dans graphql.ts. Le module ObserveModule vient du starter NestJS et ajoute de la supervision.

controllers contient les routes HTTP classiques. providers contient les classes injectables : AppService et GraphQlResolver.

3. Le contrat GraphQL

schema.graphql

Le projet suit l'approche schema-first du PDF : le schéma est écrit en premier, puis les types TypeScript sont générés.

TypeRôle
RatioTypeDéfinit un bonus de revenu, de vitesse ou d'anges.
PalierDécrit un unlock, une amélioration ou un manager.
ProductDécrit un produit achetable et productible.
WorldContient tout l'état d'une partie.

La query getWorld(user) lit le monde d'un joueur. Les six mutations correspondent aux actions prévues dans le PDF : achat, production, manager, upgrades et reset.

graphql.ts

Ce fichier est généré automatiquement depuis le schéma. Il fournit notamment les classes Palier, Product et World, ainsi que les interfaces abstraites de query et de mutation.

À retenir : ne pas modifier manuellement graphql.ts. Une régénération GraphQL pourrait écraser les changements.

4. Le monde initial

origworld.ts

Ce fichier exporte origworld, la partie utilisée pour un nouveau joueur. Il respecte l'objectif du PDF : six produits, trois paliers par produit, trois allunlocks, dix upgrades, quatre angel upgrades et six managers.

Les six produits sont Chechia, Chicha, Harissa, Fricassee, Boga et Djeba. Chaque produit possède un prix, un coefficient de croissance, un revenu, une vitesse, une quantité et des paliers.

nouveau prix = ancien prix × croissance

gain = productions × quantité × revenu
       × (1 + anges actifs × bonus ange / 100)

idcible indique le produit concerné. La valeur 0 signifie tous les produits et -1 signifie un effet directement appliqué au monde, comme le bonus des anges.

5. Le service métier

app.service.ts

@Injectable() permet à NestJS de créer le service et de l'injecter dans le resolver.

Lire et sauvegarder un monde

readUserWorld(user) cherche userworlds/{user}-world.json. Si le fichier n'existe pas, le service renvoie une copie de origworld. La copie est nécessaire pour éviter de modifier le modèle initial partagé en mémoire.

saveWorld(user, world) crée le dossier si besoin, puis écrit le monde en JSON. Le code actuel utilise une écriture synchrone, alors que le PDF présentait une version asynchrone.

Calculer le temps écoulé

updateWorld(world) compare l'heure actuelle avec lastupdate. Pour un produit sans manager, elle termine ou réduit la production manuelle en cours. Pour un produit avec manager, elle calcule le nombre de cycles automatiques terminés et conserve le reste dans timeleft.

elapsed = maintenant - lastupdate
cycles = floor((elapsed + timeleft) / vitesse)
timeleft = (elapsed + timeleft) modulo vitesse

Chaque production appelle ensuite addProduction, qui ajoute le gain à l'argent et au score.

Débloquer et appliquer les bonus

checkUnlocks vérifie les paliers du produit et les paliers globaux. Un palier individuel dépend de la quantité d'un produit ; un allunlock exige que tous les produits atteignent le seuil.

applyUpgrade choisit la cible avec idcible, puis applyBonus applique le type de bonus :

  • gain multiplie revenu ;
  • vitesse divise la durée de production ;
  • ange augmente angelbonus.

Réinitialiser une partie

resetWorld calcule les anges gagnés à partir du score, recrée un monde depuis origworld, conserve le score et ajoute les nouveaux anges à totalangels et activeangels.

6. Les opérations GraphQL

resolver.ts

Le resolver reçoit les arguments GraphQL avec @Args. Avant chaque action, il recharge le monde et appelle updateWorld afin de calculer les gains accumulés depuis la dernière action.

getWorld

  1. Lire le fichier du joueur.
  2. Calculer les productions dues.
  3. Sauvegarder le monde actualisé.
  4. Le retourner au frontend.

acheterQtProduit

La mutation vérifie l'identifiant et la quantité, calcule le prix de chaque exemplaire, déduit l'argent, augmente la quantité, augmente le prix futur et vérifie les unlocks.

lancerProductionProduit

Elle place timeleft à la valeur de vitesse. La production sera traitée lors d'une prochaine requête.

engagerManager

Elle cherche le manager, trouve son produit grâce à idcible, puis active managerUnlocked. Le produit devient automatique.

acheterCashUpgrade et acheterAngelUpgrade

La première consomme de l'argent ; la seconde consomme des anges actifs. Dans les deux cas, l'amélioration est marquée comme débloquée et son bonus est appliqué.

resetWorld

Elle met à jour le monde une dernière fois, le réinitialise avec le service et sauvegarde le résultat.

7. Routes et tests

app.controller.ts

Ce contrôleur provient du squelette NestJS. GET / renvoie Hello World!. Il sert de test de démarrage, mais ne contient pas la logique du jeu.

app.controller.spec.ts et test/app.e2e-spec.ts

Le premier test vérifie directement la méthode du contrôleur. Le test end-to-end démarre toute l'application et envoie une vraie requête HTTP à /. Ces tests ne couvrent pas encore les mutations GraphQL.
